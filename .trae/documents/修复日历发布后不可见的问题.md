
## 问题根因分析

我把发布链路（`calendar_plan_publish`）和查询链路（`calendar_query` / `calendar_mine`）完整走了一遍，发布本身没问题（正常写入数据库），**问题出在查询可见性逻辑**。

### 根因：`calendar_query` 的 `buildVisibilityWhere` 函数（`cloudfunctions/calendar_query/index.js:100-132`）

当查询 visibility 为 `"public"` 时，生成的 where 条件是：

```javascript
// 当 visibility === "public" 时（即调用方希望看到公开日历）
return _.or([
  { visibility: "public" },                                 // 任何公开计划
  _.and([{ visibility: "friends" }, identityEq])            // 自己发布的 friends 计划
]);
```

这个逻辑**本身是对的**——能查到所有公开计划。但继续看 timeline mode 第 199 行：

```javascript
if (filterGymId) baseWhere.push({ gymId: filterGymId });
```

**但注意 timeline 页面前端传参**（`miniprogram/pages/calendar-timeline/index.js:119-124`）：

```javascript
const params = {
  date: this.data.date,
  city: this.data.city,
  visibility: this.data.visibility
};
if (this.data.gymId) params.filterGymId = this.data.gymId;
```

这里有个关键点：**home 页点击日期进入 timeline 时会携带 gymId**（`pages/home/index.js:681`），而 **calendar-publish 发布成功后 redirect 到 timeline 时也只传 gymId**（`pages/calendar-publish/index.js:422`）。

发布时，`calendar_plan_publish` 写入数据库的记录里，`visibility` 字段写的是用户选的值（默认 `"public"`），`gymId` 也是正确的岩馆 ID。

让我再确认一下——**发布后 redirect 到 timeline 的完整路径**：

```javascript
// calendar-publish/index.js:419-423
const q = [`date=${this.data.selectedDate}`];
if (this.data.city) q.push(`city=${encodeURIComponent(this.data.city)}`);
if (this.data.selectedGymId) q.push(`gymId=${this.data.selectedGymId}`);
wx.redirectTo({ url: `/pages/calendar-timeline/index?${q.join("&")}` });
```

注意！这里传的参数名是 `gymId`，但 timeline 页面 loadTimeline 里读的是 `filterGymId`：

```javascript
// calendar-timeline/index.js:124
if (this.data.gymId) params.filterGymId = this.data.gymId;
```

**所以 gymId 是能正确传到 query 的**。那问题在哪？

让我再看看 timeline 页面 onLoad 的解析：

```javascript
// calendar-timeline/index.js:69
const gymId = safeText(options && options.gymId);
```

OK，gymId 确实能正确赋值到 `this.data.gymId`。那 loadTimeline 里 `params.filterGymId` 也正确传了。

**真正的根因是——timeline 查询还传了 `city`！** 看 calendar_query timeline 模式：

```javascript
// cloudfunctions/calendar_query/index.js:200
if (city) baseWhere.push({ "gymSnapshot.city": city });
```

发布函数 `calendar_plan_publish` 在发布时写入的 `gymSnapshot` 是：
```javascript
gymSnapshot = { name: gym.name || "", city: gym.city || "", address: gym.address || "" };
```

**但前端发布时没有传 city！** 看 publish 函数调用：

```javascript
// calendar-publish/index.js:395-408
const payload = {
  action: "create",
  payload: {
    mode: "gym",
    date: this.data.selectedDate,
    startTime: this.data.startTime,
    endTime: this.data.endTime,
    visibility: this.data.visibility,
    note: this.data.note || "",
    needPartner: !!this.data.needPartner,
    skillTags,
    gymId: this.data.selectedGymId
    // ← 注意！没有传 city 字段！
  }
};
```

所以发布时 `gymSnapshot.city` 取决于数据库里 `RockGyms.city` 有没有值——如果岩馆本身 `city` 为空，那 `gymSnapshot.city` 也是空。

而 timeline 查询传入了 city（如果从 home 进来的话），就会过滤掉那些 city 不匹配的计划。

**但更关键的是**——我再看看"本人看不到自己发布"和"他人看不到"的另一个可能性：

等等，让我重新审视 `calendar_query` 里的 `buildVisibilityWhere`——当 timeline 查询用 visibility="public" 时，逻辑只返回 `{visibility: "public"}` 的计划 + 自己发布的 `visibility: "friends"` 计划。**那 visibility="friends" 的计划，他人本来就应该看不到，这是预期行为。**

**核心嫌疑点回到了 city 过滤上。** 让我再确认一遍 timeline 从 calendar-publish 跳转时的 city 传值：

`calendar-publish/index.js:79`:
```javascript
const city = decodeURIComponent(safeText(options && options.city) || "");
```

`calendar-publish/index.js:421`:
```javascript
if (this.data.city) q.push(`city=${encodeURIComponent(this.data.city)}`);
```

好的，如果从 home 进来时有 city，那 publish 后 redirect 也会带 city。而 query timeline 时会用这个 city 过滤 `gymSnapshot.city`。

**问题定位：** 如果数据库里某个岩馆的 `city` 字段为空或者跟 home 页显示的 city 不一致，那即使你在这个岩馆发布了计划，因为 timeline 查询用 `gymSnapshot.city` 过滤，查不到。

另外还有一个**次要问题**：home 页点击日期跳转 timeline 时传了 visibility，但 calendar-publish redirect timeline 时**没传 visibility**，所以 timeline 用的是默认 `"public"`，这倒不是 bug，但如果用户选了 friends 可见的话就不对了。

## 修复方案

### 修复 1（主要）：`calendar_query` timeline mode — 移除或放宽 city 过滤

把 timeline 查询的 city 过滤从 `gymSnapshot.city` 改成更宽松的逻辑，或者直接**去掉 timeline 模式下的 city 过滤**——因为 timeline 已经通过 `filterGymId` 精确锁定了岩馆，不需要再按 city 二次过滤。

**改动位置：** `cloudfunctions/calendar_query/index.js` timeline mode，删除第 200 行 `if (city) baseWhere.push({ "gymSnapshot.city": city });`

### 修复 2（次要）：calendar-publish redirect 时带上 visibility 参数

**改动位置：** `miniprogram/pages/calendar-publish/index.js`，在 redirect 的 query string 中追加 visibility。

### 修复 3（可选增强）：home 页跳 timeline 时也不必强制传 city

因为已经传了 gymId（精确岩馆），city 过滤是多余且有风险的。但 home 的问题优先级低，因为用户选了岩馆后应该能看到。

---

## 实施计划

1. **改 `cloudfunctions/calendar_query/index.js`**：timeline 和 calendar 两个 mode 里都去掉 `gymSnapshot.city` 的过滤（或只对未指定 gymId 的查询才用 city 过滤）
2. **改 `miniprogram/pages/calendar-publish/index.js`**：redirect 到 timeline 时补上 visibility 参数
3. **重新部署云函数**

这样修复后，发布的计划无论岩馆 city 是否有值、timeline 查询有没有带 city，都能被正确检索到。
